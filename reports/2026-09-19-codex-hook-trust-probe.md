# Codex hook trust probe

Date: 2026-09-19
Status: isolated behavioural probe; no implementation or deployment

## Result

On the locally installed `codex-cli 0.155.1`, changing only the top-level
`description` in `hooks.json` changes neither the native hook key nor
`currentHash` nor `trustStatus`. The minimum design can therefore use a
versioned `description` envelope for non-authoritative provenance; a sidecar is
not justified by trust churn. The marker must not, by itself, authorize
deletion or ownership: it is editable, unauthenticated metadata.

This probe establishes parser/hash/status behaviour, not a real user's approval.
The matching `trusted_hash` used below was copied from Codex's own `hooks/list`
response into a disposable `config.toml`; no interactive review was performed.

## 1. Description-only change

The initial declaration was:

```json
{
  "description": "probe-a",
  "hooks": {
    "SessionStart": [
      {"hooks": [{"type": "command", "command": "/usr/bin/true"}]}
    ]
  }
}
```

The first native `hooks/list` response reported:

```text
key         /private/tmp/codex-hook-trust-probe.tfX9d1/hooks.json:session_start:0:0
currentHash sha256:5bcf5439a4b245c57c9e7f3910368077fa8b85b8231cd151f801f58f1414d57e
trustStatus untrusted
```

Changing only `description` to a provenance-shaped string left all three values
identical. After placing that exact native hash under the exact native key in
the disposable `config.toml`, a fresh app-server returned `trustStatus:
trusted`. Changing only `description` again left the key, hash, and `trusted`
status identical.

The lazy-harness reader returned the same structure before and after a further
description-only change:

```text
untrusted=()
unknown=('session_start[0]',)
stale=()
orphaned=()
ignored_events=()
unreadable=''
```

Therefore:

1. `description` is excluded from the normalized per-handler identity hashed by
   Codex 0.155.1.
2. It is excluded from the positional trust key.
3. A description-only edit does not make the native status `modified` and does
   not change lazy-harness doctor output.
4. The `trusted` observation is synthetic hash injection, not evidence of real
   approval. Lazy-harness remains correct to report a stored hash as `unknown`.

## 2. Native parser surface and preservation requirement

The schema generated by this exact binary names these event groups:

```text
PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact,
SessionStart, SessionEnd, UserPromptSubmit, SubagentStart, SubagentStop,
Stop, Interrupt
```

A matcher group has `hooks` plus optional/nullable `matcher`. The normalized
handler union is:

| Type | Accepted fields |
|---|---|
| `command` | `command`; optional/defaulted `commandWindows`, `timeoutSec`, `async`, `statusMessage`, `additionalContextLimit` |
| `mcp_tool` | `server`, `tool`, `input`; optional/defaulted `timeoutSec`, `statusMessage` |
| `prompt` | `type` |
| `agent` | `type` |

The raw minimal command omitted every optional field and parsed successfully.
`hooks/list` normalized it to `matcher=null`, `async=false`, `timeoutSec=600`,
`statusMessage=null`, and `additionalContextLimit=null`. It also projected
source, enablement, display order, hash, and trust status. That projection is
lossy: for example, it does not expose every raw handler field in every variant.

For the planned merge, preserve each valid foreign matcher-group JSON object as
read, including handler order and all native fields above. Do not reconstruct a
foreign group from `hooks/list` metadata or from lazy-harness's narrower
`HookEntry(command, matcher)` model. Event-key order and duplicate foreign
groups must likewise be retained. This probe did not establish that arbitrary
unknown fields are accepted; “preserve” here means preserve valid native fields,
not bless invented extensions.

## 3. How order and index enter trust

The observed key is:

```text
<absolute declaring path>:<snake_case native event>:<group index>:<handler index>
```

For the fixture it ended in `session_start:0:0`. The generated metadata also
reported `displayOrder: 0`, but the persisted identity is the key above. Codex's
per-handler `currentHash` is the normalized declaration identity (native event,
matcher, group/handler declaration), while persisted trust is looked up by the
positional key and then compared with that hash.

Consequences for merging:

- Reformatting JSON or changing only `description` is harmless to trust.
- Reordering groups changes which declaration occupies each positional key.
  Unless the swapped declarations have identical hashes, the stored hashes at
  those keys become `modified`.
- Inserting or deleting before a foreign group shifts its key and therefore its
  trust identity even when its declaration hash is unchanged.
- Handler order inside a multi-handler group is independently positional.
- Keeping a foreign group at the same event/group index is the trust-preserving
  operation. Relative order alone is insufficient if managed insertions shift
  its absolute index.

This supports a position-filling merge: refill existing managed slots and
append surplus managed groups only after every existing group for that event.
Appending after the last old managed slot is insufficient when a foreign group
follows it, because the insertion would still shift that foreign trust key.

## 4. Provenance decision

Use `description` for the minimal provenance envelope, with these limits:

- version the encoding and accept the legacy description;
- record only facts needed for conservative classification, such as launcher
  basenames previously emitted by this artifact;
- require both valid provenance and an exclusively recognized group before
  classifying it as harness-owned;
- treat malformed provenance, mixed groups, and unrecognized handlers as
  foreign;
- never delete a file or group solely because its free-text description claims
  harness ownership.

A sidecar would add snapshot, rollback, corruption, migration, and concurrency
surface without buying trust stability. Reconsider it only if future Codex
versions include `description` in `currentHash`, stop accepting the envelope, or
the implementation needs provenance stronger than an editable ownership hint.

## 5. Minimum reproducible test fixture

The smallest useful fixture is one temporary absolute directory containing:

`hooks.json`:

```json
{
  "description": "probe-a",
  "hooks": {
    "SessionStart": [
      {"hooks": [{"type": "command", "command": "/usr/bin/true"}]}
    ]
  }
}
```

`config.toml` starts empty. A binary-contract test should:

1. Start `codex app-server --listen stdio://` with that directory as
   `CODEX_HOME`, initialize it, and call `hooks/list` for the temporary cwd.
2. Capture, rather than hard-code, the returned absolute key and `currentHash`;
   assert `untrusted`.
3. Persist that returned pair under `[hooks.state."<key>"].trusted_hash`, restart
   the app-server, and assert `trusted`. Label this synthetic trust, not approval.
4. Change only `description`, call `hooks/list` again, and assert identical key,
   hash, and status.
5. Run `trust_for_profile` before and after the description change and assert
   identical `unknown`, `stale`, and `orphaned` fields.

For the merge unit tests, add a second `SessionStart` group with a distinct
command and keep the raw JSON as the oracle. Assert byte-semantic preservation
of the foreign group and its index. Separately swap/insert groups and assert the
derived keys change position; do not assert a real approval state in a unit
test.

## Recommendation to the implementer

Proceed with the description-envelope design and the position-preserving merge.
Compute `WriteOp.changed` from final hook arrays only, so provenance-only churn
does not request re-trust. Preserve valid foreign groups raw and in place;
classify ownership conservatively using provenance plus exact recognized
handlers. Add the disposable app-server contract test above as a version-pinned
probe, while ordinary unit tests remain binary-independent and never call a
stored hash “trusted.”
